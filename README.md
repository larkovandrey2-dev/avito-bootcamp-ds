# Поиск объявлений для Avito DS Bootcamp

## Коротко

Для каждого поискового запроса нужно вернуть подходящие объявления из отдельного
корпуса. Итоговый результат решения v4 на закрытой проверке:

**Recall@50 = 0.844391**

Это официальный результат отправки решения v4. Остальные числа ниже получены
по результатам локальных экспериментов.

Решение не пытается сразу угадать окончательный ответ одним способом. Сначала оно
собирает широкий список подходящих объявлений, затем CatBoost YetiRank выбирает
из него лучшие.

## Что требовалось сделать

В обучающих данных записано, что искал пользователь и какое объявление он выбрал.
В проверочной части запросы и объявления разделены. На выходе для каждого запроса
нужна строка из идентификаторов объявлений:

```text
"ремонт аккумулятора шуруповерта"
                 ↓
       список подходящих item_id
```

Официальная метрика — Recall@50. Она показывает, какая доля действительно
подходящих объявлений попала в выданные пятьдесят.

## Почему два этапа

У задачи есть две разные причины ошибки.

1. Нужного объявления вообще нет среди найденных кандидатов.
2. Оно найдено, но модель поставила его ниже первых пятидесяти мест.

Поэтому решение разделено на сбор кандидатов и ранжирование.

`Candidate coverage` отвечает на первый вопрос: присутствует ли правильное
объявление где-нибудь в общем пуле. Локальный `Hit@50` отвечает на второй:
попало ли единственное известное положительное объявление в итоговые пятьдесят.

На development у v4:

- покрытие кандидатов — `0.9642`;
- Hit@50 — `0.8940`.

Это контрольные значения локального запуска final v4.

## Данные и локальная проверка

В train нет `query_id`. Одинаковый видимый текст может относиться к разным
поисковым событиям, поэтому нельзя объединять все строки с одним текстом в одну
сессию и считать их общим набором правильных ответов.

Локальная проверка устроена осторожнее:

```text
видимый контекст поиска + выбранный item_id
                    ↓
       один пример с одним положительным item
                    ↓
        попал ли item в первые пятьдесят
```

Это `single-positive offline Recall@50 proxy`: полезная локальная оценка, но не
полная копия официальной метрики.

Зафиксированный протокол использует:

- development — 5 000 примеров;
- старый holdout — 1 000 примеров;
- локальный корпус — 189 212 объявлений;
- отдельный internal — 5 000 примеров для независимой проверки ранжирования.

Holdout после ранней проверки v1 больше не использовался для настройки. Benchmark
также не участвовал в выборе признаков и параметров.

## Как развивалось решение

| Версия | Что изменилось | Official Recall@50 |
|---|---|---:|
| v1 | TF-IDF по заголовку и мягкий бонус той же локации | 0.237331 |
| v2 | Несколько источников кандидатов и обучаемое объединение | 0.650562 |
| v3 | Относительные признаки и YetiRank | 0.788055 |
| v4 | Поведенческая география и сравнение отдельных текстовых полей | **0.844391** |

В таблице приведены официальные результаты четырёх отправленных версий.

### v1: понятная отправная точка

Первый вариант искал совпадения между запросом и заголовком через TF-IDF. Затем
объявления из той же локации получали небольшой бонус. На development лучший
проверенный бонус был `0.05`; официальный результат составил `0.237331`.

Главный вывод: совпадение слов действительно полезно, но одного списка недостаточно.

### v2: несколько способов поиска

Добавились плотные векторы Giga, поиск внутри локации, описание и параметры
объявления. Ручное объединение заменили обучаемой моделью. Официальный результат
вырос до `0.650562`.

Исследование также показало, что сильный сам по себе источник не всегда полезен
в готовой системе. Например, Harrier оказался немного сильнее Giga отдельно, но
не улучшил выбранную итоговую связку и был исключён.

### v3: сравнение кандидата с соседями

Сырые оценки разных запросов плохо сравнимы между собой. Поэтому модель стала
видеть не только абсолютную оценку кандидата, но и его положение относительно
остальных кандидатов того же запроса.

На одной и той же системе кандидатов переход к таким признакам и YetiRank поднял
development с `0.7332` до `0.8338`. После расширения пула итоговый development
достиг `0.8530`, а официальный результат v3 — `0.788055`.

### v4: география по поведению и отдельные поля

В v4 добавлены два блока:

- переходы между локациями, которые реально встречались в выборе пользователей;
- отдельное сравнение запроса с заголовком, параметрами и описанием.

Вместе они подняли официальный результат относительно v3 на `0.056336`, то есть
на `5.6336` процентного пункта. Эксперименты не разделяли этот официальный прирост
между двумя блоками, поэтому здесь им не приписывается отдельный вклад.

## Итоговая схема v4

```text
                         запрос
                           |
        +------------------+------------------+
        |                  |                  |
      TF-IDF          Giga-векторы       география
        |                  |                  |
        +----------- общий пул --------------+
                           |
                     185 признаков
                           |
                  CatBoost YetiRank
                           |
                    первые 50 items
```

В корпусе локальной проверки находится 189 212 объявлений. Общий пул перед
ранжированием обычно содержит несколько сотен кандидатов; точный размер зависит
от запроса и пересечения источников.

## Источники кандидатов

| Источник | Где ищет | Зачем нужен | Глубина |
|---|---|---|---:|
| Lexical | Заголовок, TF-IDF | Точные слова и короткие устойчивые фразы | зафиксировано в v4 |
| Giga | Все заголовки | Смысловое сходство без точного совпадения слов | 200 |
| Giga local | Та же локация | Не даёт объявлениям из крупных городов вытеснить местные | 100 |
| Description | Описание | Находит услугу, плохо названную в заголовке | 200 |
| Title + params | Заголовок и параметры | Добавляет формальные характеристики услуги | 200 |
| Giga local deep | Та же локация | Более глубокий местный список | 200 |
| Description local | Описание в той же локации | Совмещает текст описания и местный контекст | 100 |
| Giga geo50 | Радиус 50 км | Ищет рядом, даже если `location_id` отличается | 100 |
| Geo redirect | Типичные локации выбора | Находит реальные межгородские направления из истории | зафиксировано в v4 |

Глубины источников зафиксированы в конфигурации final v4. Там, где отдельная
численная глубина не является частью публичного запуска, это прямо отмечено в таблице.

## Поведенческая география

Точная локация, радиус и поведенческий переход отвечают на разные вопросы.

- Точная локация: объявление относится к тому же `location_id`?
- Радиус: координаты объявления находятся поблизости?
- Поведенческий переход: куда пользователи из этой локации действительно уходили
  за выбранной услугой в train?

Для последнего варианта строится таблица:

```text
search_location
       ↓
локации выбранных в train объявлений
       ↓
P(item_location | search_location)
       ↓
дополнительные объявления из типичных направлений
```

Например, пользователь ищет редкого специалиста в небольшом городе, а по истории
такие заказы часто уходят исполнителям из соседнего крупного города. Жёсткий
фильтр по равенству локаций потеряет эти варианты. Поведенческий источник просто
добавляет их в пул и оставляет окончательное решение ранжирующей модели.

## 185 признаков без перечисления всех колонок

Список кажется большим, но состоит из нескольких повторяющихся идей.

| Семейство | Что сообщает модели | Пример |
|---|---|---|
| Положение в источнике | Насколько высоко кандидат найден каждым способом | rank, reciprocal rank |
| Относительные оценки | Насколько кандидат близок к лидеру именно этого запроса | gap до top-1, z-score, percentile |
| Согласие источников | Нашли ли один item разные независимые способы | число источников, лучший rank |
| Фильтры и метаданные | Совместимы ли параметры и заполнены ли поля | совпадения фильтров, rating |
| Расстояние | Насколько далеко item от центра поисковой локации | distance, радиусные флаги |
| Поведенческая география | Насколько типичен переход между локациями | transition probability |
| Текстовые поля | Где и какие слова запроса встретились | title coverage, редкое слово |

В final v4 ровно 185 признаков: 131 базовый, 11 географических и 43 признака
сопоставления текстовых полей. Их порядок сохранён в
`artifacts/final_v4_feature_schema.json`.

## Зачем нужны относительные признаки

Оценка `0.7` сама по себе почти ничего не говорит. Если лучший кандидат запроса
имеет `0.71`, то `0.7` выглядит сильно. Если лидер имеет `0.95`, тот же кандидат
уже заметно слабее.

Поэтому используются:

- отношение к оценке лидера;
- разница с лидером;
- место внутри распределения запроса;
- z-score внутри запроса;
- согласие глобального и локального поиска.

Именно этот тип представления был главным прорывом v3: на независимой internal
проверке Logistic с относительными признаками получил `0.8234`, PairLogit —
`0.8242`, YetiRank — `0.8262` по результатам локальных экспериментов.

## Сопоставление текстовых полей

Заголовок, параметры и описание рассматриваются отдельно. Это позволяет отличить
сильное совпадение в названии услуги от случайного слова в длинном описании.

Редкие слова получают больший вес. В запросе «ремонт аккумулятора шуруповерта»
слово «ремонт» встречается у множества услуг, а «шуруповерта» гораздо точнее
описывает намерение. Модель видит, в каком поле найдено редкое слово, совпали ли
числа и латинские обозначения, и сколько слов запроса покрыто.

## Как работает YetiRank

Одна обучающая группа соответствует одному запросу. В ней есть выбранное
объявление и отрицательные объявления, которые действительно нашла retrieval-
система. YetiRank учится поднимать выбранный item относительно остальных в этой
же группе.

Параметры frozen-модели:

- depth — `6`;
- learning rate — `0.05`;
- trees — `158`;
- random seed — `42`.

Число `158` не является результатом early stopping. Это число деревьев final
v3/v4, выбранное в локальных экспериментах и затем не менявшееся.

### Retrieval100 и hard negatives — не одно и то же

`retrieval100_selection` собирает обычную обучающую группу из кандидатов текущей
поисковой системы: сохраняет положительный item, берёт представителей разных
источников и дополняет группу сильными baseline-кандидатами. Так обучение похоже
на реальное применение модели.

Отдельный эксперимент hard-negative mining специально концентрировался на самых
сложных ошибках уже обученной модели. По результатам локальных экспериментов он
оказался слабее: `0.8126` и `0.8196` против `0.8218` у обычной retrieval-выборки.

## Воспроизводимость

1. Положите исходные parquet в `data/`.
2. Создайте окружение и установите зависимости.
3. Проверьте наличие модели и кэшей.
4. Запустите воспроизведение.

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

python scripts/reproduce_v4.py --data-dir data --check
python scripts/reproduce_v4.py --data-dir data
```

Быстрый запуск использует сохранённые дорогие стадии. Полная перестройка
эмбеддингов нужна только при отсутствии кэша. Используется зафиксированная ревизия
модели Giga из `artifacts/final_v4_config.json`; seed и параметры YetiRank также
лежат в этом файле.

Переобучение на готовой матрице:

```bash
python scripts/reproduce_v4.py --data-dir data --retrain
```

Перед отправкой CSV проходит проверку: правильные колонки, полный набор запросов,
уникальные items и принадлежность всех идентификаторов benchmark-корпусу.

## Структура кода

```text
src/data.py       — строит локальные разбиения без утечки
src/retrieval.py  — ищет кандидатов разными способами
src/geo.py        — строит географические источники
src/features.py   — считает признаки пары запрос–объявление
src/ranking.py    — формирует группы и обучает YetiRank
src/pipeline.py   — соединяет этапы сверху вниз
src/utils.py      — небольшие общие функции
main.ipynb        — учебный разбор решения
```

## Ограничения

- Локальный single-positive Hit@50 не воспроизводит настоящие наборы релевантных
  items одной поисковой сессии.
- Качество ограничено кандидатами: ranker не может вернуть item, которого нет в пуле.
- Поведенческая география зависит от наблюдавшейся истории и слабее для редких
  исходных локаций.
- Полное воспроизведение без кэша требует заново считать плотные векторы.
- Число `158` и `RRF_K = 30` сохранены как часть final v4; локальные эксперименты
  не дают основания объявлять их глобально оптимальными.
