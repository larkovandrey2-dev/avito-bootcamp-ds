# Поиск объявлений для Avito DS Bootcamp

Решение задачи поиска: для каждого запроса нужно вернуть 50 объявлений из заданного корпуса. Итоговый официальный `Recall@50` — **0.844391**.

## Задача и метрика

В обучающих данных есть поисковый запрос и одно объявление, которое пользователь выбрал. В benchmark даны новые запросы и отдельный набор объявлений. Для каждого запроса требуется выбрать ровно 50 уникальных `item_id`.

Метрика `Recall@50` проверяет, попали ли известные релевантные объявления в первые 50 результатов. В train нет `query_id`, поэтому настоящие наборы релевантных объявлений одной поисковой сессии восстановить нельзя. Локальная проверка использует честный, но упрощённый показатель: попал ли единственный известный положительный объект в top-50.

## Главная идея

Решение состоит из двух этапов:

1. Несколько способов поиска собирают широкий список кандидатов.
2. CatBoost YetiRank сравнивает кандидатов внутри одного запроса и выбирает лучшие 50.

Это оказалось устойчивее, чем пытаться получить окончательный ответ одним поисковым методом.

### Поведенческое перенаправление по географии

Локация запроса и локация подходящего исполнителя не всегда совпадают. Поэтому мы не ограничиваем поиск только ближайшими объявлениями. По истории train оценивается `P(item_location_id | search_location_id)`: в каких локациях пользователи из данной поисковой локации действительно выбирали услуги. Объявления из таких направлений становятся дополнительными кандидатами.

### Сопоставление отдельных полей

Модель получает не только готовые оценки сходства. Для `title`, `params` и `description` отдельно считаются совпадения слов запроса, покрытие запроса, порядок слов и вес редких слов. Например, совпадение редкого названия модели полезнее совпадения общего слова «ремонт».

## Как развивалось решение

| Версия | Основное изменение | Official Recall@50 |
|---|---|---:|
| v1 | TF-IDF по заголовку и небольшой бонус той же локации | 0.237331 |
| v2 | несколько источников кандидатов и обучаемое объединение | 0.650562 |
| v3 | расширенный пул кандидатов и query-relative YetiRank | 0.788055 |
| v4 | поведенческая география и признаки отдельных полей | **0.844391** |

Основной скачок v2 → v3 дал не новый encoder, а правильное ранжирование: относительные ранги, разницы оценок и согласие источников внутри одного запроса. В v4 больше всего помогли поведенческая география и совпадения редких слов по отдельным полям.

## Итоговая архитектура v4

Источники кандидатов:

- word TF-IDF по заголовку;
- Giga Embeddings по заголовку;
- плотный поиск в той же локации;
- TF-IDF по описанию и по `title + params`;
- более глубокие локальные ветки;
- поиск в радиусе 50 км;
- поведенческое перенаправление между локациями.

Ранжирование:

- 131 признак источников, относительных рангов и метаданных;
- 11 признаков поведенческой географии;
- 43 признака взаимодействия запроса с `title`, `params`, `description`;
- CatBoost YetiRank: depth 6, learning rate 0.05, 158 деревьев, seed 42.

Локальные результаты зафиксированного E4:

| Проверка | Hit@50 | Candidate coverage |
|---|---:|---:|
| internal | 0.8878 | 0.9550 |
| development | **0.8940** | **0.9642** |

## Что проверяли, но не включили

- Исторический prior по тексту запроса оказался слабым и неоднозначным без `query_id`.
- Узкие ветки по microcategory добавляли мало новых положительных объектов.
- Простое увеличение глубины выдачи почти не помогало.
- Hard negatives ухудшали соответствие между обучением и реальной выдачей.
- Жёсткий фильтр локации терял межгородские случаи.
- Структурный parser фильтров дал лишь `+0.0008` internal и не прошёл порог проверки на dev.
- Cross-Encoder улучшал ранжирование, но был слишком дорогим для полного benchmark; в final v4 его нет.

## Установка

Проект проверен на Python **3.13.5**. Подойдут Python 3.11–3.13.

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

На Mac автоматически используется MPS, если он доступен. На машине с CUDA выбирается CUDA, иначе CPU. Это влияет на скорость кодирования, но не меняет логику решения.

## Запуск

```bash
python scripts/reproduce_v4.py --data-dir data
```

Результат записывается в `answer_v4.csv`. Файл содержит колонки `query_id` и `answer`; в каждом ответе строго 50 уникальных валидных идентификаторов.

```bash
# Проверить данные, конфигурацию и кэш без тяжёлого запуска
python scripts/reproduce_v4.py --data-dir data --check

# Переобучить YetiRank на готовой матрице признаков
python scripts/reproduce_v4.py --data-dir data --retrain
```

Если кэш найден, используются готовые дорогие стадии. Если отдельных файлов нет, они пересчитываются и сохраняются. Исходные parquet и submissions намеренно не входят в Git.

## Ограничения проверки

- В train нет идентификатора поисковой сессии, поэтому локальный Hit@50 — это single-positive proxy, а не точная копия официального Recall@50.
- Один и тот же текст может соответствовать разным независимым поискам; такие строки нельзя объединять в один «логический запрос».
- Benchmark не использовался для выбора признаков или параметров.
- Старый holdout после ранней проверки v1 больше не применялся для настройки.
